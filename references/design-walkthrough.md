# 系统设计导读（学习资料）

> 用途：让新读者（人或 agent）在半小时内看懂"这套系统为什么这样设计"。
> 与规范的关系：`msp/spec.md` 说"必须怎样"，本文说"为什么 + 例子"。建议对照
> [msp/conformance.md](msp/conformance.md) 的测试向量阅读。

## 1. 三层结构

这套东西不是"一个程序"，而是三层叠起来：

1. **协议（MSP）**：像 USB 标准——规定对象、行为与"绝对不许发生的事"（30 条不变量），
   不规定语言/数据库。用 50 条测试向量验收任何实现。
2. **技能（本目录）**：一份说明书，任何 agent 读它就能把协议落成一个真实项目——
   选型分支、表结构、交付阶段、每步验收、踩坑清单。
3. **生成出来的系统**（fan-platform 是实例）：模块化单体，9 个模块 + 一个数据库 + 一张 outbox 事件表。

## 2. 一条主线：小明买月卡（正常流程）

1. 下单：商品标题/价格**拍照**进订单（快照，之后改价不影响这单），状态 `pending`，15 分钟有效。
2. 支付：收款码没有订单号回调，系统给这单分配**唯一金额 199.03**（199 + 尾数 3 分），
   登记一条"199.03 归这单所有"的租约。
3. 到账：监听端发现"收到 199.03"，HMAC 签名上报；服务端验签、查时间窗，按金额匹配到订单。
4. 履约：订单 `paid`，同一事务写 outbox `order.paid`；worker 按商品类型分派：
   发权益（到期 = now + 30 天）、账本记 `+100 积分`（含 balance_after），订单 `fulfilled`。
5. 判权：小明打开会员内容，系统**只查权益表**——不查订单、不查支付记录。

## 3. 四个核心思想

- **单一事实来源**：权益由权益表决定、积分由账本决定、订单由订单状态决定，谁也不从别人那儿推断。
  删掉订单表，会员照样生效（INV-3/13）。
- **一切资金变动可重放**：余额 = 账本求和，账本只追加不修改；状态变更与事件同事务（INV-14/18）。
- **只加不改**：新商品类型/渠道/事件可以加，已有语义不能改——扩展安全的根基（extensions.md）。
- **内核闭环 + 插件注入**：内核保证"下单→支付→履约→权益→退款→对账→审计"永远走得通；
  打赏、榜单、分销等花样从 14 个扩展点注入，不动内核（plugin-architecture.md）。

## 4. 边界情况（每条对应规范编号）

**重复点击下单/支付**：同一幂等键第二次调用返回第一次的订单（OP-O1）；同一到账通知重复上报
返回 `duplicate`，权益不重发、积分不重加（INV-7，T-03）。

**卡在支付窗口边缘**：14 分 59 秒付款、监听端 16 分钟才上报。见 §5——判定用 `paid_at`，
不是上报时刻；窗口内支付 + 宽容期上报 = 命中履约；窗口外才付款 = unmatched → 举证补单（T-38）。

**提前续费不丢天数**：剩 20 天续 1 月 → 到期 = 原到期 + 30 天；过期 3 天才续 → now + 30 天；
永久权益不被订阅覆盖（INV-9，T-09~T-11）。

**续费后退款（段回收）**：订单 A 买 1 月、订单 B 续 1 月，同一行权益被顺延两次。
退 B 只回收 B 贡献的段；退 A 只回收 A 的段——绝不动其他订单的段（INV-16，T-34）。

**礼物送出一部分再退款**：买 3 送 1，只能扣回 2 → **整体回滚转人工**。
原则：宁可暂时不退钱，不能"退了钱东西还在"（INV-16，T-18）。

**并发扣积分**：余额 100，10 个并发各扣 100 → 只成功 1 个。禁止"先读余额再写回"
（条件更新/行锁，INV-11，T-26）。

**事件重放**：`order.paid` 被重试 3 次，权益发放按 `(人, 商品, 来源订单)` 幂等，
会员期只加一次（INV-26，T-31）。

**金额空间枯竭**：同一价格点只有 99 个尾数；过期订单不释放租约 → 僵尸占满空间，
新用户付不了款。所以 OP-O5 定时关单 + 释放占用（T-33）。

**两个系统共用收款账户**：同一笔 199.03 被两边同时匹配 = 双花。一个账户只能有一个匹配域（INV-8）。

**插件零改动**：做"打赏礼物 + 榜单"= 注册礼物履约处理器 + 订阅 `order.paid` 累计榜单 +
挂后台页面。内核一行不改（plugin-architecture.md §6）。

## 5. 支付窗口边缘：匹配宽容期 vs 延长窗口

结论：**推荐"匹配宽容期（report_grace）"，不推荐"延长支付窗口"**。两者不是一回事：

- `expires_at`：订单支付截止（UI 语义：过了就显示失效）；
- `reservation_ttl`：金额码租约（保护金额空间不被泄漏）；
- `report_grace`：到账上报的宽容期（补偿监听/网络延迟，默认 5–15 分钟）。

规则（OP-P2）：时间判定以 `paid_at`（支付发生时刻）为准，而非上报时刻——
`paid_at ≤ expires_at` 且上报在 grace 内 → 按命中履约；`paid_at` 晚于窗口 → unmatched，走 OP-P4 补单。
金额占用可在 `expires_at + report_grace` 后才释放（OP-O5，MAY）。

为什么不能直接延长 `expires_at`：① UI 语义混乱（用户以为还能下单）；② 推迟租约释放，
高峰时金额空间更快枯竭；③ 等于把"晚付款"也放行——而晚付款应该走人工补单而不是静默履约。

## 6. 从金额匹配迁移到真实回调（hook）

结论：**迁移成本低**，因为金额匹配被隔离在两处：`PaymentProvider` 接口实现 + OP-P2 结算入口。
其余（订单转 paid、outbox 履约、退款冲销、账本）只依赖状态与事件，不依赖"怎么匹配上的"。

你问"主要负责是不是订单和用户绑定：支付链接绑定订单 → 链接被付 → 订单对应用户付了"——
方向对，但要补三件事，否则会串单/代付错绑：

1. **回调验签**：先证明"这条回调真是支付方发的"（证书/密钥验签 + 防重放），再谈绑定；
2. **金额一致**：回调金额必须等于订单应付（INV-20）——不能只信"链接被付了"；
3. **付款人身份**：优先用回调里的付款人标识（如微信 `openid`）与订单用户核对；
   拿不到时才退回"out_trade_no → 订单"作为唯一绑定。

迁移步骤（对应 extensions.md §2.2）：换 `PaymentProvider` 实现（创建意图/查单/退款）→
结算入口从"按金额匹配"换成"按 out_trade_no 匹配"→ 金额租约表整体退役 →
webhook 丢失兜底（主动查单 OP-P3）与人工补单（OP-P4）**保留不动**——
真实 hook 只是让"自动命中"更可靠，不是让对账和兜底消失。

## 7. 自测题（看完应该能答）

1. 为什么"删掉订单表，会员依然生效"是健康信号而不是 bug？
2. 同一笔支付通知到达 3 次，系统里最多发生几次积分入账？靠什么保证？
3. 用户还剩 10 天会员时续费、然后退款续费单：到期时间应该怎么变？为什么不能整行 revoke？
4. 支付窗口从 15 分钟延长到 60 分钟，会悄悄引入什么风险？
5. 接官方网关回调后，金额租约表还需要吗？补单和主动查单还需要吗？
