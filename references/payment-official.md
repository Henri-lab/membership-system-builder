# 官方网关 / 托管计费（official_gateway / hosted_billing）

拿到商户号（微信支付、支付宝）或使用托管计费（Stripe/Paddle/RevenueCat）时的链路。**业务代码不应感知差异**——通过 `PaymentProvider` 适配器隔离：

```
CreatePayment(ctx, {OrderID, OutTradeNo, AmountCents, Subject, ExpiresAt}) → {QRPayload/PrepayID, ExpiresAt}
QueryPayment(ctx, OutTradeNo) → {Status, PaidAt, ProviderRef}
Refund(ctx, {OutTradeNo, RefundNo, AmountCents, Reason}) → {RefundNo, Status}
```

## 与个人收款码的差异

| 维度 | 个人收款码 | 官方网关 |
| --- | --- | --- |
| 到账确认 | 监听端上报 + 金额指纹匹配 | 异步 webhook（验签）+ 主动查单兜底 |
| 金额 | 必须加唯一分位 | 原价即可（订单号天然唯一） |
| 退款 | 人工转账 + 工单冲销 | API 退款 + 退款回调 |
| 订阅续费 | fixed 金额复用 + 手动续费 | 可签约代扣（周期扣款） |
| 合规 | 个人码不得用于经营性远程收款 | 合规，费率约 0.6% |

## Webhook 处理要点

1. **验签**：按渠道文档验签（微信 V3 平台证书 / 支付宝公钥），验签失败直接 4xx，不落库；
2. **幂等**：`(provider, provider_ref)` 唯一约束；重复回调返回成功但不重复履约；
3. **金额校验**：回调金额必须与 `payments.amount_cents` 相等，不等则拒绝并告警；
4. **事务**：更新支付单 + 订单 + 写 outbox，与个人收款码匹配事务完全同构；
5. **兜底**：回调丢失时用定时任务主动查单，超过 N 分钟未支付则关单；
6. **退款**：退款单状态机 `applied → processing → succeeded/failed`，退款成功事件触发**同一套冲销逻辑**（回收权益/积分/礼物）。

## 迁移路径（个人收款码 → 官方）

- `offers.meta.amount_mode` 保留：官方渠道下 `random/fixed` 都退化为"不加密金额"；
- `payments.provider` 切换新适配器，历史数据保持可读；
- 监听端并行对账一段时间后下线；
- 订阅若切到代扣，`memberships.auto_renew` 打开，并保留手动续费入口作为降级。

## 托管计费（Stripe/Paddle/RevenueCat）补充

- 商品/价格在对方平台建（Price ID 存进 `offers.meta`）；
- 不要试图在本地重建订阅周期，**以对方 webhook 为准**（created/invoice.paid/canceled）；
- 权益发放仍走本地 entitlement，事件来源记录 `provider_ref`；
- 国内访问与结算通道需单独评估。

## 接入官方回调的前置条件（中国大陆）

**先分清两条"回调"**：监听端上报（个人码模式，已经有）与官方渠道 API 回调（本节讨论）。
两者的门槛完全不在一个层面。

### 三条可选路径与门槛

| 路径 | 主体要求 | 域名/备案 | 资金流 | 适用阶段 |
| --- | --- | --- | --- | --- |
| 个人收款码 + 监听端 | 无 | 无 | 个人账户 | 验证期过渡（合规上不得用于经营性远程收款） |
| 聚合支付/持牌服务商进件 | 视服务商（部分支持小微/个人） | 通常不要求你的域名备案 | 经服务商结算 | 无执照过渡，费率略高 |
| 官方直连（微信/支付宝） | **营业执照**（个体户即可） | **ICP 备案域名 + 大陆服务器** | 商户号对公/法人账户 | 长期正式形态 |

### 官方直连的硬条件清单

1. **主体资质**：个体工商户或企业营业执照；法人/经营者身份证；对公账户或法人银行卡；
   特殊类目可能追加资质（如在线教育内容合规材料）。
2. **域名与服务器（最容易被忽略）**：
   - 需要 **ICP 备案**的域名，且**备案主体与商户主体一致**；
   - 备案要求服务器在**中国大陆**（境外节点无法备案）；
   - 域名后缀必须属于工信部批复范围——**先在云厂商备案系统里实测该后缀是否可选**，
     或查询工信部"域名注册管理机构批复"名单；不确定时直接用 `.com` / `.cn` 最稳。
3. **回调地址技术条件**（本项目已满足，属最容易的部分）：
   - 公网可达、HTTPS、回调路径无鉴权但**必须验签**；
   - **5 秒内返回成功**：只做"验签 → 幂等入库 → 写 outbox"，履约异步进行；
   - 幂等：`(provider, provider_ref)` 或 `out_trade_no` 唯一；
   - 金额一致性校验：回调金额 = `payments.amount_cents`（官方渠道不再需要金额指纹）。
4. **密钥与证书**：
   - 微信 V3：`mchid`、`appid`、APIv3 key、商户私钥与证书序列号、平台证书（定期轮换）；
   - 支付宝：`appid`、应用私钥、支付宝公钥（RSA2 验签）；
   - 全部走环境变量/挂载文件，禁止入库入日志（见 INV-18 类要求）。
5. **对账**：启用渠道对账单下载，与本地 `payments` 按 `out_trade_no` 对账；差异进入人工队列。
6. **退款**：官方渠道支持 API 退款；退款成功回调触发**同一套冲销逻辑**（不得只退钱不回收权益）。

### 自检方法（判断当前环境差多远）

```bash
# 1) 服务器属地：返回 country 必须为 CN，否则无法备案
curl -s https://ipinfo.io/<服务器IP>/json | grep country
# 2) 域名后缀可备案性：登录云厂商备案控制台尝试添加该域名
# 3) 备案状态：工信部 beian.miit.gov.cn 按域名/主体查询
# 4) 回调可达性：外网 curl -I https://<域名>/api/payments/<channel>/notify（部署后）
```

### 代码侧改造清单（本项目已有 80%）

| 项 | 现状 | 需要新增 |
| --- | --- | --- |
| 结算唯一写入口（OP-P2：验签 + 幂等 + 同事务 + outbox） | 已实现（监听端路径） | 复用同一契约，新增渠道适配 |
| `PaymentProvider` 接口（create/query/refund） | 已定义 | `wechatv3` / `alipay` 两个实现 |
| 回调路由 | `/internal/payment-notifications`（监听端） | `/api/payments/wechat/notify`、`/api/payments/alipay/notify`（公开、验签） |
| 金额指纹 | 已实现（个人码必需） | 官方渠道下退化为"不加尾数"，代码保留开关 |
| 退款冲销 | 已实现（人工审核触发） | 接入渠道退款 API + 退款回调 |
| 对账 | 有对账接口（本地账本） | 新增渠道对账单下载与比对任务 |

**结论**：官方回调的难点在资质与备案（周级、几百到几千元），代码改造是"加两个适配器 + 两个路由"的机械工作
——这正是把支付抽象成 Provider 与"唯一写入口"契约的价值。
