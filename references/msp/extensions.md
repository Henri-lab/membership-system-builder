# MSP 扩展机制

> 协议的核心承诺：**扩展只做加法**。任何声明"兼容 MSP"的实现，新增能力都不得改变既有语义。

## 1. 扩展点一览

| 扩展点 | 机制 | 约束 |
| --- | --- | --- |
| 商品类型 | `Product.type` 新枚举值 | 必须定义该类型的履约动作（OP-F1 分支）与可售校验 |
| 售卖方式 | `Offer.kind` / `meta` | 新增 kind 必须说明权益周期推导规则 |
| 结算方式 | `Payment.provider` / `channel` | 必须实现 OP-P2 的验真与幂等要求；金额指纹为**信道受限**的临时策略（仅 personal_qr 场景），必须满足 INV-8/27 租约独占、OP-O5 超时释放、退款金额不含尾数（INV-20）；接入官方网关后应当废弃 |
| 积分类型 | `PointsLedgerEntry.kind` | 每次变动仍需满足 INV-11/12 |
| 事件类型 | `x-` 命名空间 | payload 前向兼容（只加字段） |
| 多租户/多创作者 | 对象上的 `owner_ref` | 判权与结算必须按 owner 隔离；金额/积分域是否共享需显式声明 |
| 多币种 | `amount.currency` | 一单一种货币（INV-20）；跨币种必须显式换汇并记录汇率快照 |
| 试用与按比例计费 | `Offer.meta.trial_days` + `proration_behavior ∈ {none, create_prorations, always_invoice}` | 试用到期、升级/降级与 proration 语义（对齐 Stripe）；段模型见 OP-R2 ① |

## 2. 典型扩展的实施步骤

### 2.1 新增商品类型（例：`course_bundle`）

1. 在 `Product.type` 增加枚举值（实现方声明）；
2. 定义下单项校验（是否需要地址、是否限量、是否可重复购买）；
3. 在 `dispatchOnPaid` 增加分支：发放哪些权益/积分/礼物；
4. 定义退款回退动作（INV-16 要求）；
5. 在 conformance 报告里新增该类型的测试向量。

### 2.2 新增结算渠道（例：官方网关）

1. 实现 `provider` 的创建意图 / 查询 / 退款；
2. `reportSettlement` 的验真方式按渠道实现（验签/证书），但**幂等与唯一写入口要求不变**；
3. 回调丢失兜底：实现主动查单（OP-P3）；
4. 金额指纹可退化为"不加尾数"，但订单金额一致性（INV-20）不变。

### 2.3 新增积分类型（例：活动奖励 `x-campaign`）

1. 增加 `kind`；
2. 定义幂等键（事件 id + ref，或业务键）；
3. 若为赠送，明确有效期策略（过期用 `expire` 冲销，禁止直接删除历史）；
4. 复用 OP-N1/N2，不新开旁路。

## 3. 兼容性规则

- **向前**：消费者必须忽略未知字段与未知事件类型（记录但不报错）；
- **向后**：发布方不得删除字段、不得改变字段语义；语义变化 = 新 `version`；
- **弃用**：字段/事件标记 `deprecated` 后至少保留一个大版本；弃用必须在 CHANGELOG 中说明替代方案；
- **测试**：任何扩展合并前，必须通过原有全部 MUST 用例（回归约束）。

## 4. 何时需要新协议而不是扩展

出现以下情况说明超出 MSP 边界，应单独定义协议（或新增等级）：

- 需要跨组织清结算（分账、多方对账）；
- 引入二级市场/转让/拍卖等资产化语义；
- 需要强一致的多方共享账本（区块链类）；
- 复杂税务与发票体系（需专门的税务契约）。

## 5. 插件化实现的契约要求（内核 + 插件）

允许把本协议实现成"完备闭环内核 + 插件注入"（工程细节见技能目录的 `plugin-architecture.md`）。
插件化**不改变**本协议的约束：

- 插件只能**新增**类型/事件/字段/状态迁移/策略实现，禁止改变既有语义（加法原则的强化）；
- 插件必须声明能力（扩展点、事件订阅、依赖的 MSP 等级）与兼容版本范围（manifest）；
- 插件失败不得破坏内核事务；事件订阅者必须幂等、可重放，禁止阻塞主链路；
- 任何插件合并前必须通过其声明范围内全部 MUST 向量（回归门禁）；
- 多个插件占用同一扩展点的冲突必须有显式决策规则（声明顺序/优先级），禁止静默覆盖。
