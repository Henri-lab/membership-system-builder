# MSP 积分账本规范：账本是灵魂

> 本文是 [spec.md](spec.md) 的"积分"领域展开，规范级别相同（MUST / SHOULD）。
> 一句话主张：**账本是唯一事实来源，余额只是派生值**。任何实现只要违反本文，就不是积分系统的"符合"实现。

## 1. 四条根本原则

- **L1（唯一事实来源）** 积分的一切历史由账本（Ledger）承载；余额是账本的派生结果，不是独立事实。
- **L2（只追加）** 账本只允许插入（append-only）。退款、过期、纠错、活动撤销一律以**新条目**表达；
  **禁止** UPDATE / DELETE 任何历史条目。
- **L3（可追溯）** 每条条目必须能回答"谁、因何、对应哪个订单/事件"（`source` + `actor` + `ref`）。
- **L4（可重建）** 任意时刻余额可由账本重建：

  ```
  balance(principal, t) = Σ delta(principal, occurred_at ≤ t)
  ```

## 2. 两种合规实现策略（结果等价，任选其一）

**策略 A：纯账本**

- 不存余额列，读时 `SUM(delta)`；
- 读放大时可用异步物化视图/缓存，但缓存必须可随时从账本重建（缓存不一致不算违规，只要账本仍权威）。

**策略 B：物化余额 + 对账不变量**（本项目采用）

- B1 余额更新与账本写入**同一事务**；
- B2 任意事务边界上满足 `balance == Σ delta`；
- B3 提供对账入口：能对任意主体校验 B2；发现漂移时**只允许追加修复条目**（`adjust`），禁止直接改余额。

**策略 C：复式记账（资金/退款可选；积分可继续用 A/B）**

- 资金变动以 `debit(账户A) / credit(账户B)` 分录表达，账本仍是唯一事实来源；
- 余额 = Σ(借方 − 贷方) 按账户聚合；退款/拒付 = 插入反向分录，禁止改历史；
- 积分系统不必采用复式；协议只约束**结果**（可重建、不可变、可对账），机制任选。

三种策略都被判定为符合——协议约束的是**结果**（可重建、不可变、可对账），不是机制。

## 3. 账本条目（最小必需字段）

| 字段 | 语义 | 约束 |
| --- | --- | --- |
| `entry_ref` | 条目唯一引用 | 不可变 |
| `principal` | 主体（用户/组织） | 必填 |
| `delta` | 增量（整数，正=入账，负=出账/冲销） | 必须 ≠ 0 |
| `kind` | 业务类型：`recharge / subscription_bonus / redeem / refund / expire / adjust / x-…` | 扩展点，新增用 `x-` 前缀 |
| `source` | 触发来源：`event:<event_id>` / `order:<ref>` / `api:<idempotency_key>` / `admin:<operator>` | **必填**（幂等键的组成部分） |
| `ref` | 业务对象引用（订单/权益/活动） | **事件驱动条目必须填写**（MUST，见 INV-15）；其余应当填写 |
| `balance_after` | 条目生效后的余额快照 | 策略 B 必填；策略 A 可空 |
| `occurred_at` | 发生时间（UTC） | 必填 |
| `actor` | 触发者（用户/管理员/系统） | 必填（与 source 共同构成审计） |

## 4. 幂等键：单列 `ref_id` 是不够的

> 通用机制（键随重复源、原子占位与结果回放、防重地图）见 [spec.md](spec.md) §10；本节只写**账本域**的键选型。

幂等的本质是"同一笔业务事实只入账一次"。实现必须按**来源**选择结构化幂等键：

| 来源 | 幂等键 | 为什么 |
| --- | --- | --- |
| 事件驱动（支付成功、订阅赠送、活动发放） | `(source_event_id, ref)` | 一个事件可能对应多条条目（一单多项）；单列 `event_id` 会让第二条被顶掉（本项目实测踩过） |
| API 调用（管理员调整、运营发放） | `(idempotency_key)` | 由调用方提供，重试返回同一结果 |
| 业务补偿（退款冲销、过期） | `(kind, ref)`（如 `('refund', order_ref)`） | 同一业务对象的冲销只能发生一次 |

**反例（禁止）**：只给 `ref_id` 加唯一约束。同一订单在不同阶段会合法地产生多条积分记录
（首次赠送 / 每期续费赠送 / 退款冲销），单列唯一会让合法入账失败或静默丢失。

**支付回调重发的两层防线**：通知层 `(provider, nonce)` 防重放 + 入账层结构化幂等键防重复记账。两层缺一不可。

**NULL 与唯一性的坑**：部分存储引擎（如 PostgreSQL 默认）把 `NULL` 视为互不冲突——`(event_id, NULL)`
重复插入不会触发唯一约束。因此事件驱动的条目 `ref` 必须非空；确需可空时用 `NULLS NOT DISTINCT`
或等价约束兜底（INV-15）。

**与 CloudEvents 的对应**：`(source_event_id, ref)` 复合唯一，正是 CloudEvents 规定事件唯一性由
`(id, source)` 共同决定（而非 `id` 单独唯一）在本领域的同构版——一个事件对应多条入账时，
单列 `event_id` 唯一必然互相顶掉。

## 5. 余额安全与并发扣减

- **C1** 余额永不为负（除非实现显式声明透支策略并写入文档）：
  对任意主体、任意时刻 `Σ delta ≥ 0`。
- **C2** 扣减必须"**检查与扣减原子化**"。机制无关，以下任一做法合规：
  - a. 条件更新：`UPDATE balances SET balance = balance - :x WHERE principal = :p AND balance >= :x`，影响行数 0 → 余额不足；
  - b. 行锁：事务内 `SELECT … FOR UPDATE` 后校验再更新；
  - c. 纯追加 + 冲突驱动重试：以唯一键/约束冲突决定重试或拒绝。
- **C3** **禁止**"先读余额 → 应用层判断 → 再写回"（读写之间可被并发插入，必然超扣）。
- **C4** 批量多主体变动按固定顺序加锁（如 principal 字典序），避免死锁。

## 6. 冲销与纠错（不改历史）

- 退款 / 过期 / 活动撤销 → 插入**负向条目**，`kind` 标注原因，`ref` 指向原业务对象；
- 历史错误 → 插入 `adjust` 条目并在 note 写明原因与操作者，**禁止**修改旧条目；
- 净额校验：对同一 `ref` 求和应当为 0（例：赠送 `+100`、退款 `-100`）。

## 7. 对账（把"灵魂"体检制度化）

1. 定时任务对每个主体校验 `balance == Σ delta`；
2. 漂移 → 生成差异报告（主体、期望、实际、样本条目）并追加修复条目；
3. 报告留存（时间 / 主体 / 差异 / 修复条目引用），作为符合性证据之一；
4. 对账发现"负余额"属于严重违规，必须当日排查（并发扣减或事务边界问题）。

## 8. 符合性用例（assume 已并入 [conformance.md](conformance.md)）

| ID | 场景 | 期望 |

| T-26 | 并发扣减：余额 100，10 个并发请求各扣 100 | 仅 1 次成功；余额 ≥ 0；账本仅 1 条扣减 |
| T-27 | 同一支付事件重放 3 次 | 只有 1 条入账；余额与余额快照一致 |
