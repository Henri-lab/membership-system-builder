> 来源标注 `真实项目` 或 `推理`；被证伪的条目在原处标注 `[deprecated]`，不要删除。

## 架构

### L-001 独立产品之间共享"代码"，不共享"服务"
- 日期：2026-10-10｜来源：真实项目（课程站 + 粉丝站）｜分支：任意
- 结论：只有需要物理唯一的能力（账号体系、一条收款流水）才共享运行实例；业务逻辑用共享代码库（Go module）而不是共享服务。
- 为什么＋落地：共享服务会引入部署耦合与分布式一致性成本；把纯逻辑抽成独立 module（不含 SQL/路由），本地 `go.work`、线上用版本 tag，跨库只共享概念不共享表。

### L-002 模块化单体 + outbox 预留拆分点
- 日期：2026-10-10｜来源：真实项目｜分支：任意
- 结论：个人/小团队规模用一个服务 + 分层模块；模块间只通过 domain 接口与 outbox 事件交互。
- 为什么＋落地：微服务在低流量下是纯负债；模块边界 + 事件就是未来的拆分缝，真要拆时是机械动作而不是重构。

## 支付

### L-003 个人收款码必须用"金额指纹"
- 日期：2026-10-10｜来源：真实项目｜分支：personal_qr
- 结论：在应付金额上加唯一分位（199.00 → 199.01…199.99），用 `unique(amount_cents) where status='active'` 保证同一时刻一个金额只归属一个订单。
- 为什么＋落地：个人码到账没有订单号，只按整数元匹配必然冲突；签发时循环重试直到拿到未占用后缀。

### L-004 支付匹配域必须全局唯一
- 日期：2026-10-10｜来源：真实项目｜分支：personal_qr / 任意多系统
- 结论：一个收款账户只能有一个匹配消费者；两套系统监听同一账户时必须用不同账户/渠道，或分区金额后缀空间。
- 为什么＋落地：同一笔到账被两个系统同时匹配 = 双花；这条是唯一不能水平复制的能力，写进部署约定。

### L-005 固定金额是"长租"而不是"消费"
- 日期：2026-10-10｜来源：真实项目｜分支：personal_qr + 订阅
- 结论：订阅用 fixed 模式按「用户 × 报价」长租（默认 180 天）；匹配成功后保持 `active`，只解绑本次订单与支付单。
- 为什么＋落地：续费要复用同一个数字，一旦置为 consumed 续费永远匹配不上；报价改价或租约过期才作废重签。

### L-006 取消与超时必须释放金额占用
- 日期：2026-10-10｜来源：真实项目｜分支：personal_qr
- 结论：用户取消订单、支付窗口超时关单时，释放该订单未支付的 random 占用并作废支付单。
- 为什么＋落地：不释放会让可用金额空间随时间枯竭，用户会看到"金额繁忙"；顺带把固定金额排除（它不属于单张订单）。

### L-007 支付渠道要用 Provider 适配器隔离
- 日期：2026-10-10｜来源：真实项目｜分支：任意
- 结论：业务层只依赖 `CreatePayment / QueryPayment / Refund` 三个方法；个人收款码与官方网关是同一接口的不同实现。
- 为什么＋落地：从个人码升级到商户号是可预期路径，业务代码不应跟着改；退款/查单能力差异由适配器内部消化。

## 幂等与一致性

### L-008 用事务性发箱，而不是默认上消息队列
- 日期：2026-10-10｜来源：真实项目｜分支：任意
- 结论：事件与业务写入同事务（outbox 表 + worker 轮询 `FOR UPDATE SKIP LOCKED`），失败退避重试、处理器幂等。
- 为什么＋落地：MQ 会带来丢失/重复/顺序问题与额外运维；表即事件，可查询可重放。触发上 MQ 的条件：每秒上千事件、跨机房扇出、多团队独立消费。

### L-009 `ON CONFLICT` 指向部分唯一索引时必须带谓词
- 日期：2026-10-10｜来源：真实项目（生产构建中实测）｜分支：任意
- 结论：`unique(event_id, ref_id) where event_id is not null` 对应的冲突目标要写成 `on conflict (event_id, ref_id) where event_id is not null do nothing`。
- 为什么＋落地：缺谓词报 `SQLSTATE 42P10`，且只在运行时暴露；所有幂等写入都要有真实数据库的集成测试兜底。

### L-010 一单多项的幂等键不能只用 event_id
- 日期：2026-10-10｜来源：真实项目｜分支：+积分 / +礼物
- 结论：同一订单多个条目的入账用 `(event_id, ref_id)`（积分）或 `(event_id, product_id)`（礼物）唯一。
- 为什么＋落地：单列 `event_id` 唯一会让第二个条目互相顶掉；本地动作（如积分兑换）event_id 为空，不受该约束影响。

### L-011 任何余额变动 = 流水 + 余额快照，同事务
- 日期：2026-10-10｜来源：真实项目｜分支：+积分 / +礼物
- 结论：`ledger(delta, kind, balance_after)` 与 `balances` 在同一事务更新；禁止只 `UPDATE balance`。
- 为什么＋落地：只有流水才能审计、对账、冲销；`balance_after` 让对账无需重放全部历史。余额加 `check(balance >= 0)`。

## 业务域

### L-012 权益续期在「原到期与当前时间的较晚者」上顺延
- 日期：2026-10-10｜来源：真实项目｜分支：会员/订阅
- 结论：续期 SQL 用 `greatest(expires_at, now()) + 周期`；永久权益（expires_at 为 null）不被订阅覆盖。
- 为什么＋落地：否则提前续费会丢天数、永久买断会被降级；判权唯一走 entitlement（`unique(user_id, product_id) where status='active'`）。

### L-013 退款必须"钱物同步回收"
- 日期：2026-10-10｜来源：真实项目｜分支：任意
- 结论：退款审核通过时，回收权益/扣回积分/扣回礼物/取消发货单与订单退款在**同一事务**完成；回收不满足则整体回滚转人工。
- 为什么＋落地：只退钱不回收是最常见的资损漏洞；策略要写进技能正文（宁可拒绝退款也不留漏洞）。

### L-014 积分兑换也要生成订单
- 日期：2026-10-10｜来源：真实项目｜分支：+积分
- 结论：积分兑换走 `payment_mode=points` 的订单 + 同一套 outbox 履约；积分订单禁止签发收款码。
- 为什么＋落地：不新开支路，退款/后台/对账全部复用；在支付意图入口拦截 points 订单可避免"用积分又扫码"。

### L-015 收藏型礼物限量与购买必须同事务
- 日期：2026-10-10｜来源：真实项目｜分支：+礼物
- 结论：`limited_total/issued_count` 与购买在同一事务 + `FOR UPDATE` 校验。
- 为什么＋落地：异步核对必然超卖；榜单按金额（总榜 + 月榜）在同事务累计，避免事后聚合。

### L-016 实体周边必须存地址快照
- 日期：2026-10-10｜来源：真实项目｜分支：+周边
- 结论：下单时校验"地址属于本人"，发货单保存 `address_snapshot` JSON；发货是后台人工流程（不接物流 API）。
- 为什么＋落地：防改址争议；把"填单号"这一步隔离，未来接物流只改这一处。

### L-017 Next 的 rewrites 在构建期固化
- 日期：2026-10-10｜来源：真实项目｜分支：go_next_pg / node_next_pg
- 结论：`INTERNAL_API_URL` 必须在 `next build` 时注入；运行期改环境变量不生效。

## 工程与运维

### L-018 私有多模块的构建凭据只有两种干净做法
- 日期：2026-10-10｜来源：真实项目｜分支：任意（含私有 module）
- 结论：① 本机构建二进制再上传；② 容器内构建用 BuildKit secret 挂载凭据。
- 为什么＋落地：凭据不得进镜像层、构建缓存、tar 包；服务器上单独放配置文件（600）或 CI Secret，并在部署脚本里单独上传/刷新。

### L-019 Caddy 关了 admin API 时，改配置要重启容器
- 日期：2026-10-10｜来源：真实项目｜分支：single_host_compose
- 结论：`admin off` 下 `caddy reload` 不可用；改 Caddyfile 后 `docker restart` 网关，并立即验证其他站点未受影响。
- 为什么＋落地：只更新文件不会生效（配置在启动时读取），容易误判"配置写错了"。

### L-020 共享网关场景要防 Docker 网络别名撞车
- 日期：2026-10-10｜来源：真实项目｜分支：单机多项目
- 结论：多个 compose 项目都有 `web`/`api` 服务名时，接入同一网络会出现 DNS 别名冲突；只让需要被网关访问的容器接入共享网络，并起唯一别名（如 `fan-web`）。
- 为什么＋落地：别名冲突表现为"偶发打不开"，排查成本极高；数据库/内部 API 不接入共享网络，顺带获得隔离。

### L-021 凭据文件必须在创建的第一时间进 `.gitignore`
- 日期：2026-10-10｜来源：真实项目（本地提交事故，推送被拦下）｜分支：任意
- 结论：`git add -A` 会把仓库目录里的凭据一起提交；提交前用 `git show --stat` 复核。
- 为什么＋落地：本地提交也可能被后续推送带出去；出事要重写提交并轮换凭据，成本远高于提前一条 ignore 规则。

### L-022 健康检查必须打自己的容器
- 日期：2026-10-10｜来源：真实项目｜分支：单机多项目
- 结论：`curl 127.0.0.1/healthz` 在共享网关下会命中别人的服务；用 `docker compose exec <svc> wget -qO- http://127.0.0.1:<port>/healthz`。
- 为什么＋落地：部署脚本的"健康检查通过"必须真的代表新容器可用。

### L-023 同机多站点：端口错开并只绑 127.0.0.1
- 日期：2026-10-10｜来源：真实项目｜分支：单机多项目
- 结论：每个项目的数据库/缓存绑定不同的 127.0.0.1 端口（如 15432 / 15433），不对外暴露。
- 为什么＋落地：避免端口冲突的同时缩小攻击面；只有入口网关占用 80/443。

### L-026 入口网关应独立成一个项目
- 日期：2026-10-10｜来源：真实项目（把课程站内嵌的 Caddy 拆出来）｜分支：single_host_compose 多项目
- 结论：80/443 由独立的 `gateway` compose 项目持有；各应用项目只把自己的 web 容器接入共享网络并起唯一别名（course-web / fan-web），网关按别名反代。
- 为什么＋落地：网关内嵌在某个应用里时，"另一个应用加域名/上线"要改那个应用的仓库并重启它的栈，两个产品的发布节奏被绑在一起；独立后三个项目生命周期互不牵连。迁移时复用原 Caddy 数据卷（证书与 ACME 账号不重签），并记住 `admin off` 下改配置必须重启容器。

### L-027 Next standalone 在多网络容器里必须显式绑定 0.0.0.0
- 日期：2026-10-10｜来源：真实项目（网关拆分时 course-web 502）｜分支：next 前端 + 多网络
- 结论：`node server.js`（Next standalone）默认绑定 `$HOSTNAME`，而容器 hostname 只解析到**第一个网络**的 IP；容器接入第二个网络后，网关访问该网络 IP 会 connection refused。
- 为什么＋落地：显式设置 `HOSTNAME=0.0.0.0` 与 `PORT`；变更网络拓扑后用 `netstat -tln` 确认监听 0.0.0.0，而不是只看容器 Up。这类问题只在"多网络 + 按 hostname 绑定"的组合下出现，单网络时会被掩盖。

### L-028 网关要持有自己的数据卷，不要借用应用项目的卷
- 日期：2026-10-10｜来源：真实项目（清理课程站遗留卷）｜分支：single_host_compose 多项目
- 结论：入口网关使用自己的命名卷（如 `gateway_caddy_data`）；不要用 `external: true` 借用某个应用项目的卷名。
- 为什么＋落地：借用会让"应用项目的清理/迁移"与"网关证书"永久绑在一起（历史包袱清不掉）；改为自有卷后重新签发一次证书即可（Let's Encrypt 配额充足）。清理顺序：停网关 → 移走旧配置 → 删旧卷 → 启动网关验证新证书。

### L-029 把系统抽象成"协议 + 符合性判定"，而不是实现模板
- 日期：2026-10-10｜来源：真实项目（MSP v0.1 立项）｜分支：任意
- 结论：把订单/会员/积分的契约抽成与语言、中间件无关的规范——对象模型 + 操作（输入/输出/副作用）+ 全局不变量 + 事件契约 + 可执行的符合性测试向量；实现只考核其**声明范围内**的 MUST。
- 为什么＋落地：实现模板会随语言与版本腐烂，而行为契约可跨技术栈复用、可被独立验收、可用于评估第三方实现；本仓库 `references/msp/` 是第一版，课程站与粉丝站已在其覆盖的向量上跑通大部分（支付幂等、续期单调、退款冲销、积分账本等）。

### L-030 积分系统的"灵魂"是账本，且幂等键必须复合
- 日期：2026-10-10｜来源：真实项目 + 用户提出的三原则（MSP v0.1 评审）｜分支：+points
- 结论：① 账本是唯一事实来源、只追加、`余额 = Σ delta` 且可重建；② 事件入账幂等键必须是 `(source_event_id, ref)` 复合键——单列 `ref_id`/`event_id` 唯一会让"一单多项"的合法入账互相顶掉或被吞；③ 扣减必须"检查与扣减原子化"（条件更新 / 行锁 / 冲突重试），禁止先读后写。
- 为什么＋落地：余额只是派生值，物化余额必须满足对账不变量（B2）并提供修复通道（只追加 adjust，禁止改余额）。这三条已写成协议不变量 INV-23/24/25 与测试向量 T-26..T-30——"灵魂"必须可验收，否则只是口号。（v0.3.2 编号重排：现为 INV-13/14/15）

## 协议评审与对齐（MSP v0.2.0 / 技能 v0.3.2）

### L-031 事件重试会把续期顺延两次——发放/续期必须按 source 幂等
- 日期：2026-10-10｜来源：真实项目（fan-platform 代码审查）+ MSP v0.2 评审｜分支：订阅 / 任意
- 结论：权益 Upsert 的 `on conflict do update` 无条件 `greatest(expires_at, now()) + 周期`，outbox 重试同一条 `order.paid` 会再次顺延；叠加 worker 对 `failed` 事件无限重试，会员期可无限延长。
- 为什么＋落地：重试是常态不是异常，幂等必须落在 `(principal, product, source)` 上而不是"已处理"状态上。已提升至 INV-26 / OP-E2 / T-31。
- 外部参考：CloudEvents 的事件唯一性（id, source）同样按"组合唯一"而非单字段唯一。

### L-032 退款回收权益必须"段回收"，续期必须更新来源
- 日期：2026-10-10｜来源：真实项目（fan-platform refunds 模块审查）｜分支：任意（含订阅）
- 结论：续期只改 `expires_at` 不更新来源时，退"续费单"退不到权益（商家退钱、用户留权）、退"原始单"端掉后续期（用户损失已购时长），双向资损。
- 为什么＋落地：权益要按"订单贡献的周期段"建模，退款只回收本单段（下限 now）。已提升至 OP-R2 ① / INV-16 / T-34。

### L-033 quantity 语义必须在履约时折算或下单时拒绝
- 日期：2026-10-10｜来源：真实项目（fan-platform fulfillment 审查）｜分支：+points / 订阅 / +gifts
- 结论：积分包/订阅按 quantity 收钱、只发一份（多买多收少发）。
- 为什么＋落地：OP-F1 逐类型定义 `q` 折算（积分 `q×(面值+赠送)`、订阅 `q×周期`），或对不可折乘类型拒绝 q>1。测试向量 T-35。

### L-034 退款必须作废未发货单
- 日期：2026-10-10｜来源：真实项目（fan-platform refunds 模块审查）｜分支：+周边
- 结论：退款事务没有触碰 `shipments`，退钱后发货单仍 pending，可被继续发货——"退了钱货照发"。
- 为什么＋落地：OP-R2 ⑤ 要求作废未发货单；已发货的转人工。测试向量 T-32。

### L-035 超时关单与金额占用释放必须有定时任务
- 日期：2026-10-10｜来源：真实项目（fan-platform payment 模块审查）｜分支：personal_qr
- 结论：过期订单永远停在 pending、随机金额占用永远 active → 金额空间枯竭，新订单 `AMOUNT_UNAVAILABLE`。
- 为什么＋落地：新增 OP-O5 `closeExpiredOrders`（关单 + 释放占用 + 作废支付单）；INV-8/27 要求及时释放。测试向量 T-33。

### L-036 指纹尾数不得进入退款金额
- 日期：2026-10-10｜来源：真实项目（fan-platform payment/refunds 审查）｜分支：personal_qr
- 结论：`paid_amount_cents` 存的是含尾数金额，退款按它计算，每单多退 0.01–0.99 元。
- 为什么＋落地：INV-20 区分 `payable_amount`（应付、退款依据）与 `settled_amount`（实收、含尾数）。测试向量 T-36。

### L-037 fixed 金额复用必须返回既有支付单
- 日期：2026-10-10｜来源：真实项目（fan-platform payment 模块审查）｜分支：personal_qr + 订阅
- 结论：并发两张 pending 单共享一个金额码，到账按 `created_at desc` 归最新单，老单被静默搁置。
- 为什么＋落地：INV-27 租约独占——任一金额码至多绑定一张未终结支付单；复用时应返回既有 `payment_ref`（同时满足 OP-P1 幂等 SHOULD）。测试向量 T-37。

### L-038 复合幂等键里 ref 为 NULL 时不去重
- 日期：2026-10-10｜来源：真实项目（fan-platform 0002 迁移审查）｜分支：+points / +gifts
- 结论：PostgreSQL 默认把 NULL 视为互不冲突，`(event_id, NULL)` 重复插入不触发唯一约束，事件重投会重复入账。
- 为什么＋落地：INV-15 要求事件驱动条目 `ref` 非空；确需可空时用 `NULLS NOT DISTINCT` 或等价约束。

### L-039 对齐成熟先例，而不是自创语义
- 日期：2026-10-10｜来源：真实项目 + 外部标准核对｜分支：任意
- 结论：MSP 的对象/状态/事件几乎都能对齐 Stripe / Lago / Kill Bill / CloudEvents / IETF 幂等草案；无先例的只有金额指纹。
- 为什么＋落地：新增 `references/msp/prior-art.md`（映射 + 差分声明要求）；SKILL.md 增加"选中的分支必须给差分声明"。

### L-040 金额指纹是"信道受限编码"，要用最严不变量保护
- 日期：2026-10-10｜来源：真实项目 + 评审结论｜分支：personal_qr
- 结论：收款码没有附言通道，只能用金额当信道——这是自创机制，租约/释放/尾数/并发边界全靠自己兜。
- 为什么＋落地：INV-8/27、OP-O5、INV-20 与 T-33/36/37；接入官方网关后废弃该机制（extensions.md）。

### L-041 内核做成"完备闭环"，花样一律走扩展点注入
- 日期：2026-10-10｜来源：开源架构核对（Kill Bill / Medusa / Spree / Sylius）｜分支：任意
- 结论：生成的系统应抽象为"基础设施内核 + 插件"：内核保证一条完整闭环（下单→支付→履约→权益→退款→对账→审计），业务花样只通过扩展点注入，不修改内核。
- 为什么＋落地：Kill Bill 用"核心引擎 + 插件 API（OSGi 隔离）"、Medusa 用"模块/插件/订阅者/工作流"、Spree 用"促销规则/动作/计算器"、Sylius 用声明式状态机——同一个答案：单向依赖 + 注册表 + 事件订阅。已落成 `references/plugin-architecture.md`（14 个扩展点 + manifest/生命周期/失败边界/符合性门禁）。
- 外部参考：Kill Bill plugin API、Medusa architecture、Spree promotion engine、Sylius Winzou StateMachine。

### L-042 插件失败不得破坏内核事务，订阅者不得阻塞主链路
- 日期：2026-10-10｜来源：架构决策（推理 + 参考实现核对）｜分支：任意
- 结论：插件异常只影响插件自身：核心调用走明确错误契约，事件订阅者失败只重试该订阅者的事件、写 last_error；内核主链路不得因此失败。
- 为什么＋落地：outbox 重放同一事件会重跑所有订阅者，订阅者必须幂等且与主链路解耦；两个插件抢同一扩展点必须有显式冲突决策。已写进 plugin-architecture.md §4/§5。

### L-043 支付窗口边缘加"匹配宽容期"，而不是延长窗口
- 日期：2026-10-10｜来源：评审讨论（推理 + 支付系统惯例）｜分支：personal_qr / 任意
- 结论：监听延迟导致的"窗口边缘误伤"应该用 `report_grace`（默认 5–15 分钟）补偿：判定以 `paid_at` 为准，窗口内支付 + 宽容期上报 = 命中；`paid_at` 晚于窗口仍走补单。不要通过延长 `expires_at` 解决。
- 为什么＋落地：延长窗口会推迟金额租约释放（空间枯竭）、让 UI 语义混乱、并静默放行晚付款。已写进 OP-P2 / OP-O5 与 T-38。
- 外部参考：银行"支付截止 + 对账入账"分离、Stripe PaymentIntent 的 recent payment 匹配思想。

### L-044 金额匹配迁移到真实 hook：只换两处，但回调要验三件事
- 日期：2026-10-10｜来源：架构分析（Provider 接口 + 唯一结算入口）｜分支：personal_qr → official_gateway
- 结论：金额匹配被隔离在 `PaymentProvider` 实现与 OP-P2 结算入口两处；接官方网关时换 Provider + 改"按 out_trade_no 匹配"即可，订单/履约/退款/账本不动。主动查单（OP-P3）与人工补单（OP-P4）保留。
- 为什么＋落地：回调不能只信"链接被付了"——必须验签、验金额一致（INV-20）、验付款人身份（如 openid）与订单用户一致；金额租约表整体退役。已写进 design-walkthrough.md §6。

## v0.3 主题（协议扩展）

### L-045 部分退款 = 按行回收 + 总额上限，而不是"整单拆分"
- 日期：2026-10-10｜来源：评审设计（对齐 Stripe Credit Notes）｜分支：任意
- 结论：`Refund.lines` 逐行指定金额，行内按金额占比折算权益段/积分/礼物；跨工单不变量是 Σ成功退款 ≤ paid，订单 `partially_refunded` 可再次退款直到 `refunded`。
- 为什么＋落地：没有行级分摊，"退一半"无法决定回收哪一半段；没有 Σ ≤ paid 会被重复退款。已落 INV-28 / OP-R1/R2 修改 / T-39/40。

### L-046 试用转正 = 普通订单支付，proration = 补差走订单/账本
- 日期：2026-10-10｜来源：评审设计（对齐 Stripe trial + proration_behavior）｜分支：订阅
- 结论：试用（OP-T1）只发限时权益，转正（OP-T2）复用普通支付履约路径，续期用 `max(原到期, now)+周期` 保住剩余试用；升级/降级（OP-M1）按"已付×剩余占比"算 unused_value，补差必须生成订单或账本贷项，禁止直接改权益时长。
- 为什么＋落地：转正另开旁路 = 又一条要维护的成交路径；补差直接改时长 = 账本不可重建。已落 OP-T1/T2/M1 / T-41~43。

### L-047 争议冻结要按"段"冻结，败诉走账本追索
- 日期：2026-10-10｜来源：评审设计（对齐 Stripe Dispute）｜分支：Disputes
- 结论：Dispute 开启时只冻结该订单贡献的权益段（active → suspended），不得波及其他订单；won 恢复、lost 走 revoke + 账本负向 chargeback 分录（个人码阶段只记录与人工追索）。
- 为什么＋落地：整行冻结会误伤"更早订单+本单续期"的合法时段——与段回收是同一原则。已落 OP-D1/D2 / INV-29 / T-44~46。

### L-048 发票只固定"快照 + 红冲不改原票"两个资金安全点
- 日期：2026-10-10｜来源：评审设计｜分支：Invoicing
- 结论：税率/税额随订单快照（INV-2），改税率不影响已开票；红冲 = 新增负向发票引用原号，禁止修改原发票。税务引擎/管辖地规则另立契约。
- 为什么＋落地：协议管不到税务合规细节，但"快照"和"只追加"是资金与审计的底线。已落 OP-I1/I2 / T-47/48。

### L-049 多币种只加"汇率快照"，不引入换汇账本
- 日期：2026-10-10｜来源：评审设计（对齐 Stripe exchange_rate）｜分支：MultiCurrency
- 结论：跨币种结算/退款必须持久化不可变 fx_snapshot 并按快照折算；退款一律按订单原币；汇率漂移差额走 adjust 分录。
- 为什么＋落地：实时汇率事后重算会让对账永远对不平；原币退款避免了双向换汇误差。已落 INV-30 / T-49/50。

### L-052 加功能先判"字段 vs 对象"：六问 + 三个杀手测试
- 日期：2026-10-10｜来源：设计方法论（推理 + 本协议五层结构）｜分支：任意
- 结论：字段描述"是什么"，对象讲述"发生了什么"；加字段只动对象层，一旦触及"谁能改/不能违反什么/要留痕重放"就必须上对象+状态机+事件+不变量。
- 为什么＋落地：用三个杀手测试（删表重建 / 审计员 / 重放）和六问（基数/生命周期/钱权/写路径/并发重放/快照）判定；正反例子：`trial_days` 是字段而"试用状态"要状态机、`Refund.amount` 是字段而部分退款要 lines+INV-28、税率要快照不要引用。已落 `references/design-judgment.md`。

### L-050 扩展表必须与主表"同点创建"，否则履约无限重试
- 日期：2026-10-10｜来源：真实项目（实现符合性用例 T-26 时发现）｜分支：+gifts / 任何带扩展表的商品
- 结论：创建 `type=gift` 商品时必须**同一事务**写入 `gifts` 扩展行（含 gift_type 与限量）；否则订单支付成功后履约报"礼物不存在"，outbox 事件带退避无限重试——表现为"钱收了、礼物永远不到账"。
- 为什么＋落地：扩展行是履约的前置数据，不能指望运维手工补。修复 = 创建接口同事务写入 + 对历史数据做一次回填迁移（`0005_gift_backfill`）+ 符合性用例覆盖（T-26 顺带走收藏型礼物路径）。

### L-051 赠品副作用必须与"发放事实"同门槛
- 日期：2026-10-10｜来源：真实项目（实现 T-31 重放用例时发现）｜分支：会员 + 积分
- 结论：权益、赠品积分、计数器等**所有**发放副作用都必须挂在同一个"该来源已发放"的判断下；只保护主权益、让赠品按事件 id 幂等，事件重放时会重复赠送（本项目实测：订阅赠送积分差点被重放二次入账）。
- 为什么＋落地：幂等是"业务事实"级而非"单条记录"级。符合性用例必须同时断言三件事：到期时间不变 + 赠品积分不变 + 发放事实条数不变，缺一条就会漏。

### L-053 老师傅判据有权威源头：四个 I / 派生数据 / 段回收 / 实体与活动
- 日期：2026-10-11｜来源：推理产物（文献对照，出处已逐条核对）｜分支：任意
- 结论：本技能散落的"老师傅直觉"不是自创玄学，而是 Helland（Identity/Immutability/Idempotence/Interchangeability、实体=事务边界）、Kleppmann（日志为源、状态为派生）、Fowler（Effectivity/Bitemporal 段）、Evans（聚合=事务边界）与 Stripe/CloudEvents/IETF/AWS 工程实践的可操作化。
- 为什么＋落地：把文献翻译成五个可直接用于代码评审的测试（删表重建/审计/并发同发/重放/回滚）并逐条挂到 INV/ledger/T 锚点；已落 `references/master-craft.md`（含原话与出处链接），prior-art.md §5 加了理论源头指针。

### L-054 官方支付回调的门槛是"资质 + 备案"，不是代码
- 日期：2026-10-11｜来源：真实项目（核查当前部署差距）｜分支：personal_qr → official_gateway
- 结论：接官方回调的硬前置是：① 营业执照（个体户即可）；② **ICP 备案域名（备案需大陆服务器，境外节点无法备案）**；③ 域名后缀在工信部批复范围内。技术侧（HTTPS、验签、幂等、5 秒返回、同事务 outbox）反而是最容易满足的——本项目的 OP-P2 契约已具备，只差两个 Provider 适配器与两个回调路由。
- 为什么＋落地：选服务器与域名时要先做"属地 + 后缀可备案性"核查（例如服务器在境外节点、域名后缀不在工信部批复范围内，这两条都不满足直连条件）。无执照过渡路径：聚合支付服务商进件（回调不要求你的域名备案）或继续监听端模式；长期形态再迁大陆服务器 + `.com/.cn` 备案域名。详见 `references/payment-official.md` §接入官方回调的前置条件。

### L-056 技能独立上游后，副本只同步、不直接改
- 日期：2026-10-11｜来源：真实项目（开源拆分）｜分支：任意
- 结论：技能独立成上游仓库后，`platform-kit` 与 `~/.codex/skills` 都是 vendored/安装副本——所有编辑只在上游发生，然后单向同步；任何副本上的手改都会造成三处漂移。
- 为什么＋落地：同步方向在 `references/maintenance.md` §7 已反转（上游 → vendored → 安装副本）；改动流程 = 改上游 → push → rsync vendored 副本并提交 → rsync 安装副本。隐私红线：含服务器属地/域名等部署细节的条目不得进上游（L-054 已脱敏）。

### L-057 确认策略按证据强度分层：指纹是快车道，截图审核才是离线 hook
- 日期：2026-10-11｜来源：用户口述 + 设计推理｜分支：personal_qr
- 结论：个人码的到账确认不是只有金额指纹一条路；按证据强度分四层：指纹自动（零摩擦、身份盲）→ 截图凭证 + OCR + 审核（绑定流水号与付款人，相当于离线 hook）→ 聚合服务商回调（无自有备案的 webhook）→ 官方直连。低单量且有运营人手时，截图审核应为主方案，指纹降为自动快车道。
- 为什么＋落地：指纹的失败模式是「金额空间碰撞 + 付款人不可知」，截图的失败模式是「上传摩擦 + 可能伪造」，两者互补而非互斥。已落 `references/payment-confirmation.md` + conformance T-51~T-54 + SKILL.md 新增「到账确认」分支（默认 `screenshot_review`）。

### L-058 截图审核的六个实现要点：两段式上传 / 内容嗅探 / key 即权限 / blob 预览 / 限额双保险 / 复用唯一写入口
- 日期：2026-10-11｜来源：真实项目（截图审核主链落地并端到端验收）｜分支：screenshot_review
- 结论：Tier 1 的难点不在流程设计（那部分 L-057 已覆盖），而在六个实现细节：① 截图先上传拿站内相对地址，再随凭证提交，别做"填外链"；② 类型按前 512 字节嗅探，不信文件名与客户端 `Content-Type`；③ 存储 key 用 `claims/<userID>/<日期>/<随机>.<ext>`——前缀既是防穿越边界也是鉴权依据（owner 前缀匹配 + 管理员放行）；④ 预览用带 `Authorization` 的 fetch 拉 blob，不开公开地址、不引入签名 URL，自己的预览走本地 objectURL；⑤ 限额双保险（请求侧 `MaxBytesReader` + 读取侧 `LimitReader`）且错误码分层 413/415/403/404；⑥ `approve` 复用既有凭证审核的唯一写入口（订单转 paid → `order.paid` → outbox 异步发权益），不新增第二条履约路径。
- 为什么＋落地：详情写进 `references/payment-confirmation.md` §3.5。两个容易漏的推论：**金额指纹在截图主链下要保留**（它是审核时的防撞码，保证同窗口内多单金额互不相同）；**AI 预审的落点极小**（凭证表加 JSONB `ai_review` + 异步 worker + 可替换 `VisionProvider`，默认只写建议，阈值跑稳再放开自动通过）。

### L-055 设计判据进验收门槛：conformance D-1~D-5 跨等级必检
- 日期：2026-10-11｜来源：推理产物（把 master-craft 的五个测试制度化）｜分支：任意
- 结论：五个老师傅测试从"学习资料"升格为"验收规则"——`msp/conformance.md` §3 设计判据清单（删表重建/审计/并发同发/重放/回滚），任何声明等级都必须通过，不得用降级豁免。
- 为什么＋落地：T-01~T-50 是行为验收，D-1~D-5 是设计审查，两者不互相替代（测试全绿但余额表可直接删且无账本 = 仍不符合）。SKILL.md 的产出物要求与不可妥协项同步要求 D-1~D-5。

### L-059 开源知识保护的现实边界：署名 + 引用格式 + 活跃，不靠技术防盗
