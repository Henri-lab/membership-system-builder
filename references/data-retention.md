# 数据保留与删除（data retention & erasure）

> 回答三个问题：哪些数据必须永远留、哪些可以删、"个人信息删除权"怎么与只追加账本共存。
> 依据：INV-14（账本不可变）、INV-24（审计）、INV-34（个人信息与事实分离）、
> 中国《个人信息保护法》（PIPL）与通用数据保护原则（GDPR 思路，仅作参考）。

## 1. 三类数据：先分类，再谈保留

| 类别 | 例子 | 规则 |
| --- | --- | --- |
| **不可变事实** | 账本、订单快照、事件、支付/退款凭证 | 禁止 UPDATE/DELETE（INV-14/33）；只归档 |
| **可变个人标识** | 手机号、邮箱、付款人昵称、收货地址 | 独立存储；掩码优先、应请求删除 |
| **派生数据** | 余额、计数器、索引、缓存、AI 预审 JSONB | 随时可删，必须能由事实重建 |

判据就是 master-craft 的"删表重建测试"：删掉它事实还在吗？在 → 派生；不在 → 事实。

## 2. 保留期建议（默认值，按司法辖区调整）

| 数据 | 默认保留 | 到期动作 |
| --- | --- | --- |
| 账本（财务流水） | ≥ 10 年 | 归档冷存储，**不删** |
| 订单 / 发票 / 退款工单 | 3~5 年或当地税法 | 归档，不删（审计） |
| 事件日志 | 1 年在线 + 归档 | 到期归档 |
| 登录 / 操作日志 | 6~12 个月 | 到期删除 |
| AI 预审结果 | ≤ 1 年 | 到期删除 |
| 截图 / 凭证原图 | 与工单同生命周期 | 归档后降级存储；删除权请求时删除 |

## 3. 删除权 vs 不可变（核心矛盾与解法）

账本与凭证**不可变**，但里面**不得**放个人信息（INV-34）——只放匿名 `principal` 引用、
`source/ref`、金额、时间。个人信息单独存在 `users/addresses` 等可变表：

- 删除请求 = 掩码或删除 PII 表记录，账本里的匿名引用保持不变；
- 余额/权益清零 = 账本**负向 `adjust` 分录**与段回收，**禁止**直接改余额或删条目（INV-12/14）；
- 结果：个人信息删了，审计链仍然完整（谁在何时动了多少钱），只是"谁"变成了匿名 ID。

一句话：**事实可留、标识可删**。为了删除权去改账本，是把可重建性也一起删掉了。

## 4. 删除请求流程（最小实现）

1. 验证主体身份并记录请求（actor + reason + 时间）；
2. 检查未终结业务（进行中订单/退款/争议）→ 先终结或告知无法立即完成；
3. 余额/权益清零走账本负向条目与段回收（不是 DELETE）；
4. 掩码或删除 PII（手机号、收货地址、截图原图）；优先掩码（如 `138****1234`）；
5. 保留匿名化审计链，写删除记录（谁、何时、删了什么类别，**不存被删内容**）；
6. 二次验证：账本 `balance == Σ delta` 仍成立；扫描事实表无 PII 明文。

## 5. 隐私红线

- 事实表禁 PII（INV-34）；PII 与事实分离存储；
- 禁止为满足删除权而 UPDATE/DELETE 账本或凭证；
- 日志不留密钥、口令、完整银行卡号；
- 文档与示例数据脱敏：不出现真实手机号、单号、付款人昵称（pitfalls 既有条目同样适用）。
